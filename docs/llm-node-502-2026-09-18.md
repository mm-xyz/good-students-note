# p4 screen pipeline：llm-node 502／connection refused 診斷

探測日期：2026-09-18，Asia/Taipei（UTC+08:00）。本報告只記錄 endpoint、模型識別、錯誤型態、延遲與程式設定，不記錄 token、密碼或逐字稿／畫面完整內容。

## 根因結論

結論：p4 的主要故障層級已確認在 llm-node HTTP／TCP 可用性路徑；最可能是 llm-node 的 listener、llama-swap gateway 或其上游推論服務在批次期間短暫不可用。具體是服務重啟、gateway 上游失敗、模型載入／OOM，或 tailnet 路由抖動，現有唯讀證據尚不能區分；目前四個 bounded probe 都成功，也不能宣稱歷史故障已修好。

目前沒有證據支持「screen.py timeout」「錯誤 model id」「vision payload／圖片大小」是這批 502／connection refused 的主因：歷史錯誤都是立即的連線拒絕或 HTTP 502，沒有 timeout／JSON parse／429 型態；同一個 model 與 screen.py 同形 vision payload 在本次探測成功。

## 根因分類

| 分類 | 判定 | 證據與界線 |
|---|---|---|
| llm-node／HTTP route 可用性 | 已證實故障發生在此層；具體機制最可能是服務／gateway／上游瞬斷 | 426 筆錯誤全部是 connection refused 或 502；TCP refused 代表當時無法建立連線，502 代表某個 HTTP gateway 回了 Bad Gateway。現時 health、models、text、vision 均 200，表示是間歇性或已恢復的狀態，不是證明永遠穩定。 |
| model id／模型載入 | model id 可用已證實；冷載入／重啟／OOM 尚未證實 | /v1/models 列 gemma-12b，文字與 vision 都成功；回應 model 露出 gemma-4-12B Q4_K_XL 檔名。ADR-2026-08-23-802:57-63 只提供歷史冷載入約 21–31 秒與 total_slots=4，沒有本次故障期間的服務 log。 |
| request 格式／影像大小 | 不是目前錯誤的最可能原因 | 285343-byte、1920×1080 JPEG 以 screen.py 同形 messages、data URL、model、max_tokens 成功回 200；若是固定格式／大小拒絕，這個 canary 應重現。 |
| screen.py timeout | 未見為主因 | 程式 timeout 是 600 秒（:58）；本次 vision 約 27.96 秒，歷史錯誤是 connection refused／502 而非 ReadTimeout／ConnectTimeout。 |
| p4 自身併發 | 不支持是本批直接原因；共享服務併發仍未證實 | screen.py:122-142 明確一張一張送，沒有平行 worker；manifest 沒有 429。ADR-2026-08-23-802:59-70 的 > 約 10 併發→429 是歷史容量證據，不能推導本批有其他 caller 同時打滿。 |
| token／Authorization | 不是目前最可能原因 | .env 沒有 LLM_NODE_TOKEN，而專案決策是 llama-swap 不驗 token；空 Bearer header 的四次 probe 全成功。 |

- 2026-09-18 08:14:53 +08:00 的 nc -vz -G 3 100.120.197.113 8080 成功；本機 lsof -nP -iTCP:8080 -sTCP:LISTEN 沒有 local listener，這不代表遠端 listener 狀態。
- tailscale CLI 不存在；ps 在目前權限下回 macOS operation not permitted。本任務禁止 SSH、重啟／kill／修改服務，因此沒有繞過這些限制。

## 最小安全下一步

1. 暫不重跑 69 支全量 screen。先請 llm-node service owner 以 manifest 記錄的時段（manifest 內 extracted_at）對照 8080 gateway、llama-swap／llama-server 的 listener、restart、OOM、model load log；這是區分「服務重啟／上游失敗／模型載入」的最小必要證據。
2. 在服務端證明穩定後，先以單一 canary frame，再做小批、順序執行；第一個 502／connection refused 就停止，不把目前 4/4 probe success 當成長時間 SLO。現有 screen.py 沒有 retry，故先做外部 preflight／小批比直接全量安全。
3. 若仍需改善韌性，另開變更評估再考慮分離 connect/read timeout、一次 bounded backoff 與服務健康閘；本診斷沒有改 screen.py、manifest、.env 或任何服務設定。
