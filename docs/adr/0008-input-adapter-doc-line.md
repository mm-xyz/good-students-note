# ADR 0008 — 輸入轉接器：文件線接進統一管線，抽取器只做確定性、理解層跨線共用

- **Status**: Accepted
- **Date**: 2026-07-31（實作對應 Lifov 卡 #605-#608、#614、#615；#616 列 backlog）
- **Related**: CLAUDE.md 原則 6（算力分工:確定性用工具、判斷用 LLM）、原則 10（音訊線
  `.venv-audio` 重依賴隔離,本 ADR 的 `.venv-doc` 同構）、原則 12（輸入轉接器,本 ADR
  的落地條文）

## Context

專案原本只吃「音檔/影片 → 逐字稿 → 好學生筆記」一種輸入。要把 PDF/EPUB/TXT 這類
「本來就是文字」的輸入也接進同一套知識庫產線,有四個非顯而易見的架構決策要先定案:

1. 文件的「抽取」要不要跟音檔的「轉錄+清理」共用同一段程式碼路徑?
2. EPUB 章節標題從哪裡取才可靠(內文猜測 vs 檔案自帶的目錄結構)?
3. PDF 直排(traditional 中文直排)文字,PyMuPDF 預設依插入順序輸出會整頁錯亂,
   且真實掃描/OCR PDF 常見「一字一行」與「同段落被 OCR 兩次」兩種變形,要不要處理、
   怎麼處理?
4. 純掃描書(無文字層,只有頁面影像)要不要做 OCR?

## Decision

### 1. 輸入轉接器分層:抽取器 = Phase-1 確定性、理解層跨輸入共用

`scripts/session.py new <file>` 是唯一入口,依副檔名(`DOC_EXTS = {.pdf, .epub, .txt}`)
自動分流,不新增子指令、不要求使用者手動選線。分流後兩線的職責邊界:

- **抽取器(`scripts/doc/extract.py`)只做 Phase-1 確定性抽取(0 token)**:文字抽取、
  結構偵測(章節→`##`/`###`)、簡繁轉換(s2twp)、雜訊清理(頁碼/頁眉頁腳/亂碼字元)。
  **絕不呼叫 LLM,絕不自己寫摘要或好學生筆記**——這條界線與音檔線 Phase A(確定性
  清理,Python 實作)同構,呼應原則 6。
- **理解層(Step 3 enhance、Step 4 好學生筆記)跨輸入共用**:不分音檔或文件輸入,
  一律吃同一份 `cleaned.md`,套用同一套規則(零省略、字數校驗)。這是分層的核心
  收益——前段(抽取/轉錄)依輸入類型各自處理,後段(理解)只認 `cleaned.md` 這一個
  共同介面,新增輸入類型不需要重寫理解層。

拒絕的替代方案:把文件硬塞進 ASR 產物格式(偽造 SRT)再走音檔線全套 pipeline——
多一層轉換即多一層失真來源,且 Phase A/B 的清理規則(幻覺過濾、字數比率 95-105%)
是為 ASR 誤差設計的,對已經乾淨的文件套用沒有意義,純粹浪費 token。

### 2. 文件線跳過 ASR 專屬清理(transcribe/phase-a/phase-b)

`extract.py` 的輸出直接當 `cleaned.md` 使用,**不**接續跑 transcribe(不存在
`transcript.srt`)、Phase A(錯字/幻覺/亂碼過濾——這是 Whisper 聽錯才需要的修正)、
Phase B(AI 校稿——文件本來就有正確標點與斷句,不需要「補標點、合併破碎斷行」)。
`metadata.json` 新增 `source_type`(`doc`/`audio`)欄位讓下游與人工檢視分得清楚
這份 session 走了哪條線,`doc_extraction` 欄位記抽取 stats(`chars`/`sections`/
`lang`/`vertical_pages`)取代音檔線的 QAQC 字數比率門檻(文件輸入沒有 ASR 誤差,
套用同一組門檻沒有意義)。

### 3. EPUB 章名優先 toc/nav;PDF 直排逐字接續 + 近似重複 OCR 去交錯

- **EPUB 章名**(#614):標題來源優先序改成「`book.toc`(作者填的真實目錄結構,
  對應到該 spine 檔的 href)→ 對不到才退回內文第一個 h1-h3 → 都沒有才退回
  『第N章』」。內文猜測(直接抓第一個 heading 元素)不可靠——很多 EPUB 的章節
  首頁 h1 是裝飾性書名重複,不是章名;toc 是作者/出版商編輯過的權威來源,
  與 PDF 走 `doc.get_toc()` 書籤是同一邏輯,兩種文件格式的章節偵測策略對齊。
  同時要濾掉 `linear="no"` 的 spine 項(EPUB 規範定義的非閱讀順序輔助頁,如
  目錄/勘誤頁),因為 ebooklib 的 `is_chapter()` 只擋得住它自動產生的 EpubNav,
  擋不住作者手動標的 `linear="no"`。
- **PDF 直排偵測與重排**(#615):逐頁用 `get_text("dict")` 讀每個 text line 的
  `dir` 向量,y 分量 dominant(`abs(dy) > abs(dx)`)的行數超過半數即判定該頁為
  直排頁,重排順序改「欄序右→左(bbox x 中心由大到小)、欄內上→下」——不用
  PyMuPDF 預設的插入順序,那套順序在直排頁上會整頁錯亂。
  取捨的關鍵在於**真實掃描/OCR PDF 不會乖乖給你「一整欄一個 line」**:
  - 直排的每個字常被拆成獨立 text line(bbox 極窄、x 中心幾乎相同)——若逐 line
    換行輸出會變成「一字一行」不能讀,故先依 x 中心把排序後相鄰的 line 分組成
    同一直欄候選(粗容差)。
  - 部分 OCR PDF 對同一段落跑了不只一次辨識,重複 pass 的 bbox 有些微 x 偏移
    (實測約 0.3–0.5px),剛好落在粗容差內,若直接依 y 排序輸出兩份 pass 的字元
    會**逐字交錯**(比一字一行更難讀)。解法是三段式收斂:①用更緊的 eps 把候選欄
    再細分子欄(能靠 x 偏移分開的重複 pass 這步就分開);②子欄內依 y0 間距把
    「同一視覺位置的替代讀值」(x 也完全相同,純粹 OCR 判讀分歧)收斂成一份;
    ③子欄還原後的文字若高度相似(difflib ratio > 門檻),視為同一段落的重複 pass
    只留較完整的一份,文字不相似則視為兩個真的不同的物理欄,原樣保留。
  - 拒絕的替代方案:整頁一次性 OCR 重新辨識(丟棄 PyMuPDF 已抽出的文字層)——
    這份文字層通常是可用的,問題只在「排列順序」與「重複 pass」,重新 OCR 是
    殺雞用牛刀且會引入新的辨識誤差,不如在既有文字層上做幾何層面的重排與去重。

### 4. 純掃描書(無文字層)OCR 路線暫列 backlog(#616)

`extract.py` 對掃描 PDF(文字密度過低)只印 WARN、不嘗試 OCR;`figures.py` 會把
掃描頁整頁渲染成 PNG 供人工或未來的 VLM 流程續接,但**本次不接 OCR 引擎**——
沒有找到符合專案「本地優先、免費、零 API key」慣例(呼應 Auth 雙軌總表、原則 6)
的現成免費 OCR 方案(雲端 OCR API 多數收費或有配額限制,本地開源 OCR 對繁體
直排古籍/掃描件的辨識品質未經驗證)。決策為明確標記已知缺口、留 backlog 卡,
不為了「功能完整」倉促接一個品質未知的方案進主管線。

## Consequences

- 新增輸入類型(文件)不需要碰音檔線既有程式碼——`if not is_doc:` 分支原封不動
  搬進既有邏輯,doc 分支是全新程式碼路徑,零迴歸風險由 `run_all.sh` 音檔線既有
  測試組 + 文件線新測試組共同把關。
- 理解層(enhance/notes)天然支援未來任何新輸入類型,只要新抽取器產出符合
  `cleaned.md` 慣例(繁體 markdown、`##`/`###` 章節)即可接上,不需要重新設計
  Step 3/4。
- 代價:文件線目前沒有「補充修正表」的使用者入口——`extract.py --corrections`
  存在,但 `session.py new` 不透傳這個選項;需要手動改字時只能事後編輯
  `cleaned.md` 或直接呼叫 `extract.py`,不在本次範圍內補齊。
- 純掃描書仍然不可讀(只能拿到頁面圖片,沒有可編輯文字),#616 解決前這類輸入
  的可用產出僅止於 `figures.py` 渲染的 PNG。
