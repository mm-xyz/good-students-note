## 一、Apps Script 選型與唯讀護欄

### 脈絡

MM 剪 podcast 時，人審 cutplan.md 的實際介面是 Google Drive 上的集數副本。
Drive 網頁版不能編輯 `.md`，MM 得回 Mac 開文字編輯器才能勾選/加刪除線——
手機、平板、外出時段全部剪不了，人審的節奏被綁在「有沒有帶電腦」上。

人審實際只做兩件事：翻勾選（`- [x]` ↔ `- [ ]`）、對贅字加刪除線
（`~~文字~~`）。其餘欄位（block id、時間碼、`[Speaker]`、逐字稿文字、
`## ✂`/`## 🎵`/`## ⚙`/`## 🎬`/`## 章節` 這些結構行）動不得——
`scripts/audio/render_cut.py` 的 `validate_program()` 會逐 block 把
cutplan.md 的文字跟 `cutplan.json`、來源 SRT 逐字比對，文字或時間碼被改壞
直接 FAIL。在桌面編輯器上這個 FAIL 訊息 MM 看得到；在手機上如果哪天真的
手滑改到一個字，MM 可能要等到出片失敗甚至出片但內容跑掉才發現。

### 決策

#### 1. 用 Google Apps Script Web App，不做獨立 web app + OAuth

Apps Script 直接跑在 MM 的 Google 帳號底下，`DriveApp` 存取 Drive 檔案不需要
自己申請 OAuth client、管理 refresh token、擔心 token 外洩或過期。部署出來
是一個 `script.google.com/macros/.../exec` 網址，MM 加到手機主畫面就是一個
「App」。

代價：UI 只能用 Apps Script 的 `HtmlService`（一支 HTML 檔案送到 iframe），
沒有現代前端框架、沒有 hot reload、除錯要看 Apps Script 的執行紀錄。這條線
音檔處理全程 stdlib/ffmpeg、零 npm 依賴（見 `scripts/tests/run_all.sh`），
一個純 HTML + vanilla JS 的小工具跟這個技術選型一致，不需要為了開發體驗
引入 Node 後端 + 前端框架 + 自架 OAuth 這一整套。

#### 2. 做專用介面，不做通用 markdown 編輯器

如果做一個通用 `.md` 編輯器（textarea 直接編全文），MM 在手機上一樣可以
手滑改到逐字稿文字或時間碼，跟現在拿桌面編輯器開檔案沒有本質差異——只是
換了個地方犯同一種錯,而且手機打字比桌面更容易誤觸。

專用介面把「勾選」「加/去刪除線」做成 UI 唯二的互動元件（checkbox、一個
浮動按鈕），id/時間碼/speaker/逐字稿文字全部渲染成不可編輯的純文字。**唯讀
是護欄,不是省事**——設計成「MM 想改壞都很難」，比「相信 MM 不會手滑」
更可靠。

#### 3. 唯讀護欄做兩道,不只信任前端

前端 UI 只暴露兩個互動元件是第一道;但如果只做到這裡,前端一有 bug（例如
selection 座標算錯、re-render 邏輯出錯）壞資料一樣會被送到後端寫進 Drive。
所以 `Code.gs` 的 `saveCutplan()` 在覆寫檔案前,拿 Drive 上「現在」的版本跟
前端送來的新內容各自解析、逐行比對——只放行「block 的 `mark` 改變」與
「block 內文拿掉 `~~` 標記後文字不變」這兩種差異,其他一律拒絕寫入並丟出
具體是哪一行、哪個原因。這道檢查重用跟 Node 測試相同的 `cutplan-core.js`
(`parseCutplan`/`splitStrikes`)——Apps Script 專案裡的 `.gs`/`.js` 檔共享
全域命名空間,`cutplan-core.js` 原封不動部署成伺服端檔案就能被 `Code.gs`
直接呼叫,不需要另外重寫一份驗證邏輯。

#### 4. 語意真相源是 Python,JS 只是另一個消費者

cutplan.md 的格式（LINE_RE、speaker 前綴、` ← 理由`、`~~刪除線~~` 配對規則）
唯一真相源是 `scripts/audio/cutplan.py`（產生）與 `scripts/audio/render_cut.py`
（`parse_program`/`parse_strikes` 解析、驗證）。`cutplan-core.js` 的正則與
拆解邏輯照抄這兩支檔案的規則,不自創第二套語意。差一處:Python 的
`parse_strikes` 用「去空白字元座標」記錄刪除線範圍(給後續換算時間碼用);
JS 版的 `splitStrikes` 保留空白字元座標(給瀏覽器 DOM 選取直接用)——這個
差異只存在於 JS 自己的內部資料結構,不影響寫回 Drive 的 `.md` 文字本身,
`render_cut.py` 讀到的 markdown 語法完全相同,不需要 JS 端知道 Python 端的
座標系統,兩邊各自獨立解析、輸出格式一致即可。

### 後果

- 好:MM 剪輯不再被「有沒有帶電腦」卡住,人審節奏可以碎片化。
- 好:兩道唯讀護欄讓「手機手滑改壞逐字稿」這個風險在寫入 Drive 前就被擋掉,
  不必等 `render_cut.py` FAIL 才發現。
- 代價:`cutplan-core.js` 要同時滿足 Node 測試與 Apps Script 瀏覽器端兩種
  執行環境,而 Apps Script `HtmlService` 只能內嵌 `.html` 檔案,所以多了一份
  `cutplan-core-inline.html`(同一份原始碼包 `<script>` 標籤)。用
  `tests/inline-sync.test.js` 逐 byte 比對防止兩份漂移,`tools/build-inline.js`
  是唯一產生方式,不靠人工複製貼上維持同步。
- 代價:部署仍需要 MM 手動跑一次(`clasp push` 或手動貼上 + 走一次 Google
  帳號授權流程),AI 不能代跑——`DriveApp` 的存取範圍要 MM 本人的帳號同意。
- 尚未落地:沒有離線編輯、沒有多裝置同時編輯的版本衝突偵測(`saveCutplan`
  是後寫覆蓋)。單人使用場景風險低,先不做;真的變成多人協作再回頭補。


## 二、刪除線互動模型：選取即套用、復原就近浮動（同日修正，取代第一節舊版「反白 → 點按鈕」互動細節）

### 脈絡

第一節（Apps Script 選型）上線後 MM 在手機上實測，同一天內連續回報三輪意見：

1. 「可以了」（勾選 + 加刪除線的基本功能可用）之後接著回報兩個 bug：
   「可以把文字選取之後直接標記/取消標記刪除線，一段一段刪除
   `~~1~~ 23 ~~4~~` 就不能批次取消」「現在也沒辦法取消標記」。
2. 兩個 bug 修完、部署上線、MM 實測「可以了」之後，提了新需求：
   「然後我可以選取了就自動 +- 刪除線嗎」。
3. 自動套用的實作方案定案途中，MM 追加一條：復原按鈕不要固定在畫面某處，
   要浮動貼在剛才選取範圍的右上角。

這三輪回饋收斂出的最終互動模型，是本 ADR 要記的決策。

### 決策

#### 1. 取消刪除線：碰到就整段拆，不要求選取邊界對齊

初版設計（第一節定案當時）要求反白範圍**恰好等於**一整段 `~~…~~` 的內文，
才判定為「取消」，其餘一律當「不合法選取」拒絕。這個設計在鍵盤/滑鼠上
勉強堪用，在手機上幾乎完全失效——MM 兩個 bug 報告的根因是同一個：**觸控
長按拖曳幾乎不可能把選取的頭尾精準對齊到字元邊界**，於是絕大多數真實的
「選取一段刪除線想取消」操作都落進「不合法」分支，UI 上就是「選了也沒
反應」。

新語意：選取範圍內只要**碰到**任何既有刪除線（完全包含它、被它完全包含、
部分重疊、或橫跨多個刪除線片段皆算），就把每一個被碰到的片段**整段**拆掉
`~~`——即使選取只蓋到該片段的一部分。選取範圍內原本是一般文字的部分不受
影響（這個操作只拆既有標記，不會順便新增）。完全沒碰到任何刪除線的選取，
才是「加刪除線」。

**教訓，值得留下來給以後的互動設計參考**：在觸控裝置上，任何要求「選取
邊界精準對齊到某個像素/字元位置」才算合法的互動設計，在真實使用情境下
約等於不可用——長按拖曳的落點精度天生就是模糊的，設計時要假設輸入是
「大概圈到了那個東西」，不是「精準框住了那個東西」。

#### 2. 反白即套用，不用再點按鈕

剪一集要對數百處贅字加刪除線，「反白 → 找按鈕 → 點按鈕」三個動作里最後
一步是純粹的重複勞動。改成：選取穩定後直接呼叫既有的 `toggleStrike`，
語意完全不變（見決策 1），套用後主動清掉選取，避免同一次選取重複觸發。

代價：選取本身不再是「預覽」，一旦系統判定選取穩定就會真的動筆。這個代價
由決策 3、4（就近浮動的復原按鈕、不設自動淡出）吸收——做錯了要能立刻、
不費力地復原，比做之前給你機會反悔更符合這個工具的實際使用節奏（剪輯時
注意力在聽音檔和讀文字上，不在小心翼翼地確認每一次選取）。

#### 3. 選取穩定判定策略

`selectionchange` 在拖曳選取控制點（handle）的過程中會連續觸發，不能一有
變化就套用——iOS Safari / Android Chrome 的選取控制點可以拖著反覆調整
範圍，一放手就套用會變成「連續套用又取消」。這是有風險的互動設計問題，
先查 prior art 再動手：

- **Robert Knight**（Hypothesis 網頁註解工具作者）2016 年的跨瀏覽器
  selection 事件測試筆記：`selectionchange` 本身分辨不出「還在調整」跟
  「調整完了」，必須搭配 `touchend`/`mouseup` 這種「手指/滑鼠放開」的
  完成訊號一起用；2019 年他自己留言確認同一套邏輯在現代瀏覽器上仍然
  可用。
  <https://gist.github.com/robertknight/ad9f1bca8280b3fa325817aa3ed9935c>
- **W3C `selection-api` repo issue #146**（"Having a matching `selectend`
  event?"）：瀏覽器目前沒有原生 `selectend` 事件，開發者普遍的作法是
  `selectionchange` + debounce/timer，疊加 `mouseup`/`touchend`/
  `pointerup` 當完成訊號——這條 issue 本身就是在推動瀏覽器原生支援，
  現況（2026）仍未落地。
  <https://github.com/w3c/selection-api/issues/146>

兩份來源收斂到同一個共識：**沒有單一事件能代表「選取結束」，要組合
`selectionchange`（持續追蹤）+ 完成訊號事件（判定穩定）**。採用的具體
策略（`scripts/cutplan-editor/Index.html` 內「選取穩定判定」註解區有完整
實作）：

1. `selectionchange`（拖曳全程連續觸發）→ 重新排一個保底 debounce 計時器
   （450ms）。這條專門處理鍵盤選取（桌機 shift+方向鍵）——鍵盤選取沒有
   pointer 事件可以當完成訊號，只能純靠「一段時間沒有再變化」判定。
2. `pointerup`/`touchend`/`mouseup`（手指/滑鼠放開）→ 排一個短很多的計時器
   （60ms），取代保底的那個——放開了就是強訊號，不必等 450ms，手機上等
   那麼久會感覺明顯 delay。
3. `pointerdown`/`touchstart`/`mousedown`（再次按下）→ **立刻取消**任何
   還在等待的計時器。

第 3 條是這兩份 prior art 之外自己補的——文件/issue 討論的都是「單次選取
何時算完成」，沒有處理「放開後很快又抓住 handle 二次調整範圍」這個情境。
如果不擋，使用者放開手指想拖 handle 微調範圍時，那個 60ms 的短計時器可能
在手指再次按下之前就先套用了，把選取清掉、搗亂正在進行的調整動作。加了
這條防線後，最壞情況只是「多套用一次、可以直接點復原」，不會弄壞資料—
—時序判定本來就是 best-effort 的 heuristic，不是精確保證，靠「可逆」
兜底比靠「猜得更準」更省成本。

#### 4. 復原按鈕：浮動貼在剛才選取範圍的右上角，不用固定的 bar

理由是視線邏輯：剪的時候注意力停在正在處理的那段文字上，undo 要就近才
點得到；固定在畫面某處（例如底部工具列）的按鈕要求使用者移開視線去找，
等於把自動套用省下來的那次點擊又還回去了。

實作上（`Index.html` positionUndoFloat）：用 `Range.getClientRects()` 的
**第一個** rect（選取起點那一行）而不是 `getBoundingClientRect()`（多行
選取時後者是含中間行滿版寬度的整體外框，會偏離「剛剛選的那裡」的直覺），
貼在該 rect 的右上角，並做 viewport 邊界 clamp（太靠右/靠上緣時往內收，
太靠近上緣時改貼下方）。

**定位座標系選了「文件座標（絕對定位，跟頁面內容一起捲動）」而不是
「視窗座標（捲動就消失）」**：剪輯是斷續的，人可能盯著聽一段音檔才回頭
決定要不要復原；如果捲動看別的段落時按鈕就消失，會讓人誤以為沒得復原了。
代價是如果後續有其他跟這個位置無關的編輯動作改變了版面高度，按鈕位置
理論上可能跟目標文字對不準——目前的操作集合（checkbox 只切透明度不改變
卡片高度）不會觸發這個問題，記在 README 已知限制，未來加新的版面相關
操作時要回頭檢查這個假設。

#### 5. 不設自動淡出計時器

復原按鈕出現後**沒有**時間到就消失的邏輯。消失只有三個明確觸發點：下一次
套用移到新位置、使用者點了它（復原一步、堆疊還有東西就跳到下一個位置）、
存檔成功。理由跟決策 4 同一條線：使用者決定要不要復原的時間不是系統能
預測的，自動淡出等於系統替使用者決定「你應該已經想好了」，這在剪輯這種
斷續、需要反覆聽音檔比對的工作節奏裡是錯的假設。

#### 6. undo 堆疊：多步、存檔成功後清空

`cutplan-core.js` 的 `createHistory`/`pushHistory`/`popHistory`/
`canUndo`/`peekHistory`/`applyStrikeWithHistory`/`undo` 是純函式，history
存的是**套用前的完整文件快照**（而不是「反向操作」）——`toggleStrike` 的
`remove` 分支在決策 1 的新語意下一次可能拆好幾段刪除線，算反向操作容易
出錯，存快照最簡單也保證復原後的文字跟套用前逐 byte 相同。每筆記錄額外
帶 `lineIndex`/`start`/`end`（套用當下的邏輯位置，不含任何 DOM 參照），
給 UI 層換算浮動按鈕該畫在畫面哪裡用。堆疊支援連續多步復原；復原到底之後
再復原是使用者正常會做的事（不是程式錯誤），優雅回傳「這次沒做事」而不是
丟錯；存檔成功後堆疊清空——已經落地的編輯不需要再回頭復原。

#### 7. 唯讀護欄不隨互動模型改變而放寬

`Code.gs` 的 `findIllegalEdit_` 是獨立於前端互動決策的最後一道防線：無論
前端是「點按鈕才套用」還是「選取穩定自動套用」，寫回 Drive 前都要拿 Drive
上現在的內容跟送來的新內容逐行比對，只放行 block 的 `mark` 改變、或 block
內文「拿掉 `~~` 之後的文字不變」——這是這個設計最重要的安全性質，**前端
互動怎麼改都不能去動這道護欄**。自動套用不代表「前端保證正確就不用再驗」
——前端的時序判定是 best-effort heuristic（見決策 3），真正保證資料不被
寫壞的是這道跟互動方式完全脫鉤的後端結構驗證。

### 後果

- 好：MM 剪一集數百處贅字，每處省一次「找按鈕、點按鈕」的動作。
- 好：取消刪除線從「幾乎不可用」變成「碰到就能取消」，貼近觸控裝置選取
  精度天生模糊的現實。
- 好：復原就近浮動,不必因為找固定按鈕而把視線從正在處理的文字移開。
- 代價：選取穩定的判定是時間 heuristic，理論上存在極端情況誤判（系統忙、
  事件延遲），但後果被「可逆 + 不改變護欄」兩層吸收，不是資料安全問題，
  是體感上偶爾多一次復原的問題。
- 代價：`pointerdown` 取消計時器這條是本次新加的，沒有被 prior art 直接
  驗證過，靠的是「最壞情況可復原」的論證而不是「這個做法本身被廣泛驗證」
  ——如果 MM 未來還是常常踩到「二次調整被打斷」，代表 60ms 這個短計時器
  數字或這條防線的觸發範圍需要再調。
- 尚未落地：復原按鈕位置只在套用當下算一次，沒有隨後續版面變化動態重算
  （目前操作集合不會觸發這個問題，見 README 已知限制）。
