# ADR-2026-09-07-asr-segmented-transcription — 遠端 ASR 分段轉錄；零標點另循 prompt 解

- 識別碼：ADR-2026-09-07-asr-segmented-transcription
- 日期：2026-09-07
- 狀態：已採納（2026-09-07 當日修訂：成因判斷推翻重寫，見「被推翻的假設」）
- 相關：ADR 0005（word timestamps 守衛鏈）、
  記憶 `whisper-prompt-style-transfers-to-output`（prompt 風格會傳染給輸出）

> 實作由轉錄線（good-student 線）落在 `transcribe_llmnode.py`；ADR 由剪輯線於同日
> 收尾時補寫，實測數字引自轉錄線的紀錄與其對照實驗。

## 脈絡

批次轉 55 講課程音檔，**21 講整份逐字稿零標點**，而且是非黑即白——有標點的每 10–12
字一個，沒有的就是 0 個。這不是品質下降，是下游直接壞掉：短句切分
（`split_words_to_phrases`）靠標點與 ≥0.5s 停頓找切點，沒有標點就切不出 cue。

同時另一個獨立問題：**長檔單次跑 whisper 會讓 ssh 連線撐不住**，106 分鐘那集實測失敗。

### 成因：prompt，不是音檔長度

對照實驗（同音檔、同模型 large-v3-turbo-q8_0、只換 prompt，各跑兩次數字完全相同——
貪婪解碼是決定性的）：

| prompt | 長度 | 字數 | 標點 | 密度 |
| :--- | ---: | ---: | ---: | :--- |
| 純敘述一句 | 21 字 | 2520 | 217 | 每 11.6 字 |
| 敘述＋少量專名嵌在句中 | 62 字 | 2481 | 211 | 每 11.8 字 |
| 敘述＋一長串專名列舉 | 147 字 | 2309 | **0** | — |

62 字版帶了專名照樣正常 ⇒ 代價來自**「列舉」這個形式**，不是專名本身。寫成有標點的
散文還不夠，**還必須短**；尾巴掛一長串頓號分隔的清單就會把整份輸出帶成不標點。

### 被推翻的假設（留作教材）

本 ADR 初版把成因寫成「`--prompt` 只條件化第一個 30 秒窗口，長音檔中途滑進不標點模式
後自我延續到結束」，並據此把分段轉錄列為**產物正確性的必要條件**。

**那個結論是錯的。** 反證：把中招的那一段音檔**單獨拉出來**（390 秒）、帶同一份長
prompt 跑，前 90 秒就是 0 標點。單段獨立執行也照樣沒有標點 ⇒ 不可能是跨段漂移，
**切段完全解決不了這件事**。

會誤判是因為兩件事同時發生（清單型 prompt ＋ 長檔），而分段確實讓長檔跑得完；
「跑得完」被讀成「修好了」。同一份 prompt 只有 21/55 中招也助長了誤判——那個
21/55 至今沒有解釋，但它不構成漂移的證據。

## 決策

**兩件事分開處理，不要混為一談。**

1. **零標點 → 改 prompt。** `context.txt` 控制在 **60 字上下**，寫成有標點的自然敘述，
   專名**嵌在句子裡**，不要寫成頓號分隔的列舉清單。規則寫在兩支轉錄腳本的
   `--context` 讀取處；`[:200]` 是程式的硬截斷**不是安全長度**（147 字沒被截斷卻已經壞掉）。

2. **長檔穩定性 → 分段轉錄。** 切 ~7 分鐘一段分別轉錄，段落 JSON 的 `offsets`（毫秒）
   平移回全域時間軸再合併。理由是 ssh 撐不住整支長檔，以及失敗只賠一段而不是整集。
   `--segment-seconds` / `--max-segment-seconds` 預設 420/480：切 420s 一段；尾巴併進
   最後一段避免孤兒段；併完超過 480s 就對半切。

分段的四個不變量是產物正確性，已用 `test_transcribe_llmnode.py` 鎖住（0.1s–6000s 全掃）：

| 不變量 | 壞掉的後果 |
| :--- | :--- |
| 完整覆蓋 `[0, duration)` | 逐字稿少一段話 |
| 段落不重疊 | 同一句被轉錄兩次 |
| 每段 ≤ 上限 | 單段過長，ssh 斷線問題回來 |
| 無孤兒段（≥ 上限/2） | 只有幾秒的尾段轉出來多半是雜訊 |

### 沒有選的做法

- **靠分段解決零標點**：已被 390 秒單段實驗推翻，見上。
- **把 `[:200]` 調小當保險絲**：成因是書寫形式不是字元數，用數字擋會擋錯東西——
  62 字帶專名是好的，147 字帶列舉是壞的，中間沒有一條可靠的長度線。規則放在
  context.txt 怎麼寫，驗收放在標點密度。

## 後果

- ⚠️ **驗收一律看標點密度**，不要只看有沒有出 SRT。零標點時 cue 數、總字數、時間軸
  單調性、簡繁轉換全部正常，只有標點密度會暴露（正常中文每 10–40 字一個）。
- ⚠️ `batch_llmnode.sh` 是 resume-safe 的（`transcript.srt` 非空就跳過）。**已經產出的
  零標點逐字稿不會自動重轉**，改完 prompt 要重跑得先刪掉那些 `transcript.srt`。
- 短音檔（≤ 480s）仍是單段一次跑完，不會多付 ssh + whisper 啟動成本。
- 段落邊界切在固定秒數上、不對齊字界：跨邊界的字可能在兩段都被切壞。一小時的材料
  約 8 個邊界，代價可接受；要更保險得做重疊窗口＋去重，目前沒做。
- 遠端逐段指令用 `;` 串接、whisper 輸出丟 `/dev/null`，單段失敗不會中止整批，靠取回
  階段的「第 N 段沒有 JSON」偵測。診斷訊息因此只知道哪一段失敗、不知道為什麼。
