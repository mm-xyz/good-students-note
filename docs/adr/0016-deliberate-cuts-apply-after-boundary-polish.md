# ADR 0016 — 人審點名的剪除，一律在邊界微調之後才套

- 日期：2026-08-11
- 狀態：已採納
- 相關：ADR 0005（word 時間戳保護鏈）、ADR 0010（停頓預設剪掉）、
  ADR 0001（cutplan 是人審真相源）

## 脈絡

2026-08-11 MM 實聽：「滿多字已經標刪除線了，但是卻還是有聽到，ex: B0180 有
『就是』還是會聽到，**而且是常態**」。

查證屬實，而且是核心功能大規模失效——EP16 的 146 處刪除線只有 39 處（27%）
真的生效，**77 處（53%）完全沒剪掉**，30.1 秒該消失的音訊還在成品裡。這個行為
從字級精剪上線以來就存在，**過去每一集都中**。

### 機制

原本的順序是「先剪、再微調邊界」：

```
subtract 後       (750.48, 751.12) (751.6,  752.92)   ← 「就是」已剪掉，缺口 0.48s
refine_boundaries (750.55, 751.155)(751.615, 752.86)  ← 谷底微調把切點推到 751.155
word_guard 後     (750.55, 751.58) (751.54,  752.94)  ← 切點落在「就是」裡面 → 推到詞尾外
merge(0.05) 後    (750.55, 752.94)                    ← 兩段重疊，合併 → 刪除線完全失效
```

`word_guard` 的職責是「不要切在字中間」，它做得完全正確——問題是
`refine_boundaries` 把**人審刻意製造的切點**微調進了那個字，於是 word_guard
忠實地把邊界推出去，等於把要刪的字塞回去。

這不是誰寫錯，是**兩個各自正確的機制被排在錯的順序上**。

## 決策

**邊界微調（snap／谷底／word 保護）先做，人審點名的剪除最後才套。**

```
ranges = snap_boundaries(...)          ← unit 邊界對齊靜音
ranges = refine_boundaries(...)        ← 能量谷底微調
ranges = word_guard(...)               ← 不切在字中間
ranges = subtract(ranges, removals)    ← ★ 刪除線 ＋ 停頓收緊
ranges = subtract(ranges, manual_cuts) ← ★ `## ✂`
ranges = merge_ranges(min_gap=0.05)
```

判準是**誰說了算**：邊界微調是機器對「unit 從哪開始／到哪結束」的猜測，可以被
修正；刪除線／`## ✂`／停頓收緊是人審點名的區間，說了算，不該被任何保護機制
覆寫。

`## ✂` 手動剪除**本來就已經**放在 `word_guard` 之後，原註解寫得很清楚：
「人審點名的區間說了算，不受『whisper 說這裡有字』的保護攔阻——那正是它要救的
失效情境」。同樣的道理適用於刪除線與停頓收緊，當初只是漏了。

## 驗證

```
修正前  146 處刪除線 → 77 處（53%）完全沒剪掉，30.1 秒殘留
修正後  163 處刪除線 →  6 處（ 4%）完全沒剪掉， 0.2 秒殘留
        語音長度 31:04 → 28:40
```

回歸測試 `test_strike_survives_boundary_polish`：合成 session 裡被刪除線標記的
字不准出現在 `--dump-ranges` 的任何保留段內。退回舊順序會變紅。

## 後果

- 好：人審的每一種「點名剪除」語意一致——標了就一定剪掉。
- 好：三種剪除（刪除線／停頓／`✂`）走同一條路徑，不必各自記得放在哪一步。
- 代價：剪點不再保證落在字界外。刪除線的邊界本來就是 word 級時間戳算出來的
  （`strike_removals` 用 words.json），停頓收緊自己也有 word 保護，所以實務上
  仍然切在字與字之間；但**如果未來新增第四種人審剪除，它得自己負責邊界合理性**。
- 代價：既有成品全部帶著這個 bug。要修得重出——EP15／EP17 若重出會自動吃到
  修正（連同 ADR 0014 的 `enforce_monotonic`）。
